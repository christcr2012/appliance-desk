# MCP and RTC contract — target version 1

All types/names below are **planned**, not existing exports. Prefix `appliance_`; canonical resource is `https://robinsonappliancerentals.com/api/mcp`. Local fixture URLs use localhost with separate credentials and issuer. Never select production from a caller URL.

## One dispatch pipeline

`decode -> validate schema -> authenticate -> current principal -> scope/policy -> input/target permissions -> preview or reserve operation -> locked reauthorization -> domain command -> readback -> redacted audit/result`.

Use a server-constructed `AgentContext`:

```ts
type AgentContext = {
  actorId: string; grantId: string; connectionId: string;
  instanceId: string; environment: 'test' | 'production';
  scopes: readonly string[]; policyVersion: number;
  correlationId: string; transport: 'mcp' | 'rtc' | 'monitor';
};
type PageInput = { cursor?: string; limit?: number; fields?: string[]; detail?: 'summary' | 'full' };
type MutationInput = {
  requestKey: string; expectedVersion: number;
  dryRun?: boolean; confirm?: boolean; previewId?: string; approvalId?: string;
};
```

These context properties are not accepted as business tool arguments. `limit` default 20/max100, opaque validated stable keyset cursor; input unknown fields rejected. `requestKey` 16–128 URL-safe characters generated by the client; store keyed digest, never a token-shaped value. `expectedVersion` is the target version; multi-target preview captures all source versions.

MCP transport uses official SDK, a pinned supported protocol set and runtime schema validators. Structured tool data and text carry the same sanitized outcome. SDK validation errors remain protocol errors; business refusals use tool errors with machine-readable codes. Tool annotations are discovery hints, never enforcement. Do not advertise subscriptions/tasks/background capabilities until supported and tested.

## Diagnostic DTO

```ts
type DiagnosticFact = {
  id: string; kind: string; severity: 'HIGH'|'MEDIUM'|'LOW';
  status: 'OPEN'|'ACKNOWLEDGED'|'RESOLVED'; version: number;
  summary: string; safeDetail: string; ruleKey?: string;
  observedAt: string; lastSuccessAt: string|null; nextExpectedAt: string|null;
  evidenceKind: 'APPLICATION_RECORD'|'PROVIDER_VERIFIED'|'OWNER_ATTESTED'|'UNKNOWN';
  failureCode?: string; failureStage?: string; correlationId?: string;
  setup: { missingNames: string[]; invalidNames: string[]; actionPath?: string };
};
```

No inference that “no recent errors” means healthy. Include provenance and uncertainty. Opaque refs identify sensitive runs/blobs without exposing storage paths or private customer IDs. UTC data plus local display values for America/Denver; money integer minor units plus display.

## Recovery action registry

First allowlist: `RUN_DIAGNOSTIC_SWEEP`, `RETRY_DATABASE_BACKUP`, `RETRY_MEDIA_COPY`, `PAUSE_AUTOMATION`, `RESUME_AUTOMATION`, `VERIFY_RECOVERY_ARTIFACT`. Backup/media retries may incur storage/transfer cost; preview says so and honors user policy. Each action maps to a real command and verification adapter, not an arbitrary cron URL or `work` callback provided by the caller. Resume previews disclose customer/provider side effects of the selected rule. Do not expose generic billing replay through this allowlist; later native adapters preserve independent money/reconciliation authorization.

`VERIFY_RECOVERY_ARTIFACT` validates manifest/checksum/readability in place; a real restore rehearsal targets an independently provisioned disposable database through engineering tools. No restore-over-production action exists in the initial registry. Disaster recovery design remains a later explicit capability with full target verification; do not mislabel a checksum as restore proof.

## RTC adapter

Implement all paths and envelope details from upstream RTC 1: manifest, tools/search/describe/call/read-only batch, whoami, OpenAPI meta surface≤30 operations, result handles. Prefix `appliance_`; modes test/production, profiles read_only/everyday/full; list defaults compact<5000 tokens and optional catalog. Derive manifest counts and available areas from the actual catalog; advertise RTC 0/not-yet-conformant until MCP-9 conformance passes. `devTools:false` until genuine development seed/cleanup tools exist. Owner `admin_overview` and `where_is_setting` are required.

HTTP door accepts only RTC passes, MCP door only connector tokens. Do not reuse the legacy key endpoint or accidentally let a pass authenticate owner browser actions. Connector/pass settings survive refresh. >8KB results return bounded first part plus owned 24h handle. Use RTC codes and `logged.id`; add typed domain details inside results without changing the envelope. Unknown authorization/resource details are not revealed in error strings.

The direct MCP dispatcher additionally supports explicit per-action approvals and delegated policies. RTC always requires its wire confirmation for marked writes; never silently relax the contract. Same action from any door must produce the same native business effects and permission refusal.
