# M-3 — Card payment for shop sales

Design: `docs/designs/BATCH-M.md` M-3 and `docs/designs/M-3-STRONGER-MODEL-PROMPT.md` (the stop rule S-M2 is answered by the
new, separate webhook branch below). Test mode only; nothing live is turned on.

## Acceptance
- Desk sale page (`/desk/sales/[id]`, owner/admin): "Pay by card" opens Stripe's own card page for exactly what is still
  owed. Refused for a cancelled, paid or zero-balance sale and for anything that is not a shop sale. Walk-in sales work from
  the desk (no Stripe customer is created for the walk-in record).
- Portal: a customer with an account can pay their own open shop sale with the existing "Pay now" button; a walk-in sale has
  no portal payment; another customer's sale looks like a missing one.
- Asking again for the same amount returns the same Stripe request (idempotency key
  `local-invoice-checkout-<invoice>-<cents>-<desk|portal>`); a new owed amount makes a new one. An audit row records each page.
- Webhook (`checkout.session.completed`, `async_payment_succeeded`, `async_payment_failed`): money is counted only when
  Stripe says the session is paid. It is recorded through the normal receipt path (source STRIPE, allocations, invoice
  status) once per Stripe charge and once per payment intent, so repeated or reordered events change nothing. The session's
  customer must match the sale's customer. If the sale was cancelled, written off or already paid when the money arrives it
  is held for the owner (the existing held-payment flow: send back to the card, mark paid, or credit); if more than what is
  owed arrives, only what is owed is applied and the extra becomes account credit. A failed bank payment records no money.
- Refund: an existing Stripe refund of a card payment on a shop sale goes to the same charge (proved by test).
- Tests: `tests/local-invoice-checkout-integration.test.ts` (real Postgres, fake Stripe, 9 tests).

## Not in this card
- A browser test (`e2e/local-invoice-card.spec.ts` in the old plan) and the real Stripe test-mode observation: the latter
  is a row on the owner checklist (needs Chris's Stripe test keys). Live Stripe stays off.
- No `ProviderOperation` row for creating the page (the design asked for kind `LOCAL_INVOICE_CHECKOUT`). Creating a payment
  page moves no money and Stripe's idempotency key already makes a retry return the same page; a new operation kind would
  need its own reconciliation wiring for no safety gain. Recorded here as a deliberate difference.
- Other local invoices (job or custom bills) still say "Pay as arranged"; only shop sales get a card page.
