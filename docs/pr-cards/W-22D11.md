## Exact current integration and acceptance

- `signing-payment-settlement.ts` proves signing cash and a frozen agreement's first-month entitlement (D8/D9).
- `signing-first-invoice-gate.ts` blocks all positive prepaid cases from generic recurring billing (D10). A customer-wide credit is **not** safe because one client may have multiple agreements/properties.
- `checkout.ts:startRecurringBillingForAgreement` already owns first delivery, agreement row locking, provider idempotent subscription creation and post-provider transaction.
- `webhooks-base.ts:mirrorStripeInvoiceLines` maps real Stripe invoice lines into local `InvoiceLineItem`. Existing `CREDIT` line kind and amount fields are reused. Never use a fake local `Payment` or a generic `CustomerCredit` for this prepayment.

## Implementation proof contract

1. Build one negative, nontaxable, nondiscountable `add_invoice_items` entry on the **same subscription create request** carrying agreement, frozen-order SHA and receipt ID metadata; never send a separate balance mutation that can reach a sibling property's invoice.
2. Keep same deterministic `subscription-create-{agreementId}` idempotency and existing provider claim; no provider call until signed status/entitlement and tax readiness pass under agreement lock.
3. Read back the resulting **actual first subscription invoice** and its entire set of lines. Demand exact subscription/customer, TEST, `subscription_create`, one matching negative metadata line, exact cents/receipt/fingerprint; an incomplete page or changed object is UNKNOWN, not applied or paid.
4. Transactionally persist the provider IDs/receipt identity in immutable `SigningFirstInvoiceApplication` after agreement subscription ID is set; SQL verifies the frozen entitlement and subscription agreement. Never mark an invoice PAID as part of credit application; actual Stripe invoice settlement remains webhook owned.
5. The webhook mirror must reject signing credits before this exact application exists, then classify the verified negative provider line as local CREDIT with a readable description. No duplicate credit on renewal or webhook replay.
6. UNKNOWN provider outcomes retain operation ID and (if known) provider object ID for reconciliation, avoid a second collection attempt, and put an owner-visible `billingBlockedReason` into To do.
