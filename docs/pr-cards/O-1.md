# O-1 — Settings history with guarded undo, and the Switches page

Design: `docs/designs/BATCH-O.md` (D-O1, D-O6). Built as one PR. M-3 is a formal dependency in the work index but is
stopped (S-M2); nothing here uses it, so this is built now (AGENTS rule 10).

## Acceptance
- `/desk/settings/history` (owner and admin): every `settings.update` / `settings.undo` audit row, newest first, in plain
  words with the real field labels ("Delivery fee: $45.00 → $50.00"), who and when (Denver time).
- **Undo this** re-applies the old value of ONE field from ONE change, in a transaction that locks the settings row,
  re-checks the staff actor (OWNER/ADMIN), refuses when the field changed again, and writes a `settings.undo` audit row.
  It only writes `BusinessSettings` (stop rule S-O3). Only an allowlist of everyday settings can be undone (profile,
  service area, fees, late fees, prepay discounts, referral reward, hold days, visit length, pickup/out-of-service days);
  agreement terms, tax approvals, signing policy, customer-email switch and security never can. Hidden buttons say why.
- `/desk/settings/switches` (owner and admin), read-only: customer email, email service, SMS, automatic renewals, paused
  automations, card payments (test/live from the key prefix; the key is never read into the list), two-step sign-in
  roles, books start date; who last changed each and a link to where to change it. No new switches.
- Tests: `tests/settings-undo-integration.test.ts` (wording, undo one field, undo twice refused, changed-again refused,
  staff refused, non-undoable field refused, switches list has no secrets). Both pages are in the accessibility route list.

## Added in the follow-up PR (owner controls and quality lane, 2026-10-24)
- **Preview before undo.** "Undo this" opens a check screen showing the setting now → what it will go back to, the
  plain-words effect, and "Nothing has been changed yet"; only "Yes, undo it" writes. A refused undo now says why
  (before, it failed silently).
- **Stale-save protection.** Each section save (Business profile, Service area, Rental policies) carries a fingerprint
  of just the stored fields that section saves, taken when the page opened. If somebody else saved those fields since,
  nothing is written and the owner is told to reload (what they typed stays in the form). Changes to other sections
  or background bookkeeping on the same row never cause a false conflict. An undo confirmed after the setting moved is
  reported as a conflict, not a generic refusal.
- **"Preview changes" button** on those three sections: lists each field that would change (old → new) and what it
  affects ("agreements already signed keep their terms"), without writing anything.
- **Switches page** now also lists launch-list emails and the Colorado tax rate lookup, and shows who last changed
  paused automations and the books start date.
- Tests: `tests/settings-preview.test.ts` (pure), `tests/settings-undo-integration.test.ts` (preview writes nothing,
  conflict, stale section save, no false conflict, new switch rows), `tests/settings-section-actions.test.ts`,
  `tests/settings-form-retry.test.tsx`, browser `e2e/owner-settings-history.spec.ts` (phone width, keyboard, axe).

## Still not covered (written down, not hidden)
- Section forms outside Business profile / Service area / Rental policies (Terms policy, Pickup billing, Job
  scheduling, notices) keep their own save paths without the preview step. Agreement terms, tax approvals, signing
  policy, customer email and security can never be undone from history (they have their own screens and rules).
- The Stripe row still reads the key prefix (test or live) only; it never reads or shows the key.
