# K-CASH-3 — Bank matching, completed statement proof and conservative cash readiness

Frozen original approved scope from `docs/designs/BATCH-K-CASH.md` §§3.2, 3.3, 4.1 and §8, against merged K-CASH-1/2 baseline `78b3de99cc6484a97498327865649ecde0fd3d50`. The owner approved roadmap engineering October 19; external bank enrollment, payments, production banking edits, paid services, messaging and unscheduled releases remain separately restricted. This is **one whole original substantial roadmap subsection**; no K-CASH-4A pre-implementation.

## Acceptance criteria (frozen before runtime changes)

1. Owner/ADMIN can view bounded same-bank suggested matches using persisted CashAccount.bankMatchWindowDays (0–30, default 7), exact signed cents and Colorado day difference, with explicit source/date/account display; no suggestion is an automatic posting or approval.
2. OWNER/ADMIN can atomically confirm a many-to-many BankMatchGroup with at least one bank observation and one journal bank line, same account, same sign, equal nonzero signed sums, live role/version checks, stable account→sorted observation→sorted journal locks and active-partial-unique claims. Concurrent retries and second claims refuse or return stable idempotent identity without partial match.
3. An explicitly reasoned group void restores claimability and observation status when the matched period is still open; the original group, items, actor and audit evidence remain available. Groups touching completed reconciliations require owner reopening the applicable period first; historical linked journal entries are never edited.
4. OWNER/ADMIN may ignore only proved duplicate/non-account bank rows with a stated reason; unknown income, unmatched expense, payroll, loan, interest or ambiguous transaction cannot be ignored to make a statement reconcile. Existing expense/receipt/typed source links are provided, not guessed accounting entries.
5. OWNER can create and complete dated statement reconciliation only with an attested opening book balance, explicit acknowledgement of existing outstanding items, sequential contiguous statement range, verified import-through evidence, bank-observation status completeness, independent bank-observation and matched-journal signed totals and zero-cent difference; no fabricated plugs, and no overlapping/gapped completed ranges.
6. Completion retains immutable source-linked balance, import, match IDs, date, actor, counts and SHA-256 evidence snapshot; a reasoned OWNER reopen leaves old revision readable, invalidates affected later reconciliations and corresponding cash-readiness labels while preserving earlier source journal/export evidence, then permits ordered re-completion.
7. Read-only cash eligibility from each registered business bank uses last completed statement ending balance plus only cleared/matched later inflows, subtracts all later journal bank outflows and pre-statement outstanding outflows exactly once, includes only subsequently matched earlier inflows, subtracts unreleased holds, and never treats Stripe clearing, undeposited money, promised rent or personal accounts as spendable cash. Missing/stale evidence, unresolved money, unsupported provider types and negative net display UNKNOWN/BLOCKED rather than a positive green funding claim.
8. Owner/admin mobile bank-check workspace provides account, unmatched observation/source register, matching suggestions and many-to-many confirmation, reasoned ignore/void, statement date/opening/closing/confirmation, full history/reopen and cash-readiness drilldown. STAFF/CUSTOMER cannot access; ADMIN cannot set owner-only opening/reopen policy, and errors are accessible without leaking private bank evidence.
9. Pure and disposable PostgreSQL tests prove same-account/sign/date, 1:M/M:1 exact sums, claim concurrency/replay/void, strict ignore, DST cutoff, gap/overlap/ending mismatch/outstanding guard, persisted immutable revision/reopen cascade, cash funding exclusions and permission boundaries; mobile Playwright/axe and full exact-head CI/review are mandatory, with owner/provider real bank evidence acceptance separate.
10. Update STATUS, work-index, decision log, owner guide, database/backup notes and release acceptance honestly; existing K-CASH-1/2 verified merge must be recorded without implying K-CASH-3 deployment, owner bank selection, external transfers or live account authorization.

## Look before building

Reuse Prisma `BankObservation`, `BankMatchGroup` / `BankMatchItem` partial active SQL uniqueness, `BankReconciliation`, `CashHold`, `CashAccount`, `JournalLine`, account limits, existing authenticated bank Cash desk, business-date helpers, `assertActiveTeamActor`, `postForSource`, backup-recovery and audit patterns. No parallel journal or unsourced money. New SQL migration only if an acceptance line cannot be proven with existing schemas and historical tracking.

## Implementation and gates

Plan-only commit first; build scoped matching + statement/reopen + conservative cash-readiness in one finance domain and mobile screen, then real-Postgres tests for source money, permissions, double-submit, period and DST; pure math and browser/a11y, route shards/owner guide/recovery/docs. Source commits never to main. Review whole diff, run repo preflight if local tooling exists; use exact-head GitHub CI and independent review before merge. Do not weaken or skip a failing test. K-CASH-4A follows K-CASH-3 merger. Owner/customer/provider acceptance queue stays independent.
