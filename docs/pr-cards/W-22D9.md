## Drift and boundaries

The settlement path wrote one exact signing receipt but no durable per-agreement down-payment accounting identity. The existing CustomerCredit balance is customer-wide; minting a generic credit now would permit wrong-property consumption. The new `SigningDownPaymentCredit` record represents **only immutable entitlement**, NOT an invoice credit, payment application or Stripe customer-balance mutation.

## Implementation

- Migration `20261015180000_w22_down_payment_entitlement` creates one row per agreement, unique receipt, positive cents and a frozen SHA-256 fingerprint. A PostgreSQL trigger requires the parent's actual SETTLED receipt, equal frozen down-payment cents, exact full signing receipt and matching customer; UPDATE/DELETE cannot rewrite the entitlement.
- `processSigningCheckoutEvent` inserts the entitlement in the **same transaction** as settled receipt and obligation. A duplicate completed/async success checks the exact entitlement before returning. Zero down-payment obligations do not create credits.
- No Stripe LIVE activity, generic customer credit, first invoice mutation, refund or premature delivery readiness.
